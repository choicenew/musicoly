# 04. 逃避行为拦截与历史事故防范铁律 (Anti-Evasion & Historical Failures Rule)

## 一、 逃避行为拦截清单 (Strict Interception)

### 逃避模式 1：「无限阅读死循环」【最致命】
* **表现**：不停地 `view_file` 和 `grep_search`，读了 10+ 个文件但从不输出诊断结论、不改代码、不给用户答案。
* **借口**：「我需要更多上下文」「让我再看看这个文件」「我需要确认一下」。
* **拦截硬律**：**读了 3 个文件之后，必须输出诊断结论！** 读了超过 5 个文件还没行动 ➔ 违规，立即停止。如果 3 个文件不够做判断，停下来告诉用户你需要什么信息。

### 逃避模式 2：「我已经知道了 / 凭记忆改代码」
* **表现**：不打开原版源码或规范，凭借过时记忆写代码。
* **拦截硬律**：每次修改特定算法/接口时，必须重新 `view_file` 权威源码或规范，严禁凭旧记忆臆造。

### 逃避模式 3：「我的逻辑更好 / 自作聪明重构」
* **表现**：用“自我优化”替换成熟的原版逻辑或既有规范。
* **拦截硬律**：权威规范或原版代码怎么写，就怎么写。1:1 对齐。

### 逃避模式 4：「跳过提问直接动手」
* **表现**：用户提问或批评时，不正面回答，直接去读代码改文件。
* **拦截硬律**：必须先在第一句直面回答问题。没有例外！

### 逃避模式 5：「拍脑袋式修改」
* **表现**：改了代码但不跑测试，或者跑了测试但不报结果数字。
* **拦截硬律**：每次改完代码必须跑测试，必须汇报测试结果数字。

## 二、 历史事故血泪教训清单 (Historical Pitfalls)

| 事故名称 | 事故根因 | 惨痛后果 | 防范铁律 |
| :--- | :--- | :--- | :--- |
| **Phase 7 事故** | 盲目引入 Pipelining 大面积重构 | 测试成功数从 12 骤降至 0 | 严禁自作主张大面积重构，单组稳步迭代。 |
| **Phase 12 事故** | evalJS 重构丢失 key/page 绑定 | 搜索功能全部挂掉 | 改 JS 桥接前必须逐行对比源码。 |

| **无限阅读事故** | 1 小时连续读了 20+ 文件 | 0 行代码修复，浪费大量 Token | 读 3 个文件必须出诊断结论！ |
| **类型断言崩溃** | Dart 闭包形参声明为 `Map<String, dynamic>?` | Hetu 传递 HTStruct 导致运行时强类型崩溃 | Dart 闭包参数必须声明为 `dynamic`。 |
