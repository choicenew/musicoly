# Incident Triage & Root Cause Analysis Protocol (故障分诊与根因精准定位协议)

## 0. 核心定位与原则
本规约对标 Google/Meta 生产环境故障分诊与 SWE-agent 缺陷定位机制。
**核心原则**：当用户给出错误日志、崩溃堆栈、异常截图或粗粒度缺陷反馈时，**AI 严禁充当无头苍蝇！严禁去翻 Git commit、严禁去读无关的 Git log、严禁漫无目的扫全局文件**！必须遵循工业级漏斗式四步定位法，直击案发现场。

---

## 第二章：执行阶段细则

### 1. 第 1 阶：第一案发现场定位 (Crash Site Anchor)
* **日志/堆栈场景**：
  1. 瞬间从堆栈中提取属于项目自身业务代码的最顶层文件路径与行号（过滤掉第三方 SDK 内部深层调用）；
  2. 提取核心异常类型（如 `NoSuchMethodError`、`NullPointerException`、`StateError`、`403 Forbidden`）。
* **截图场景**：
  1. 提取界面上的具象文字或组件特征（如特定的 Card 标题或状态文案）；
  2. 直接检索该文案对应的视图组件，锁定展示层文件。
* **绝对红线**：在输出【第一案发现场：文件路径+行号】之前，**绝对禁止调用 Git 历史命令，绝对禁止漫游式读取无关文件**！

### 2. 第 2 阶：案发现场 360° 审讯 (Root Cause Analysis)
* 使用文件查看工具，**只查看案发点前后 30 行代码**，立即进行“根因四问”：
  1. **入参溯源**：发生崩溃的对象是从哪里传进来的？
  2. **时序状态**：该变量是否在异步未完成前就被提前消费了？
  3. **边界异常**：是否因为飞行模式、空数据、权限拒绝等极端边界触发？
  4. **责任归属**：这是前端展示层的容错不足，还是上游协议/解析器交付的数据污染？

### 3. 第 3 阶：同类影响面穿透排查 (Cross-Handler Audit)
* 绝不满足于“只改报出错误的那一行代码”！
* 必须全管线检索：系统中是否存在并行的其他 Handler、通知构建器、后台服务或备用分支存在一模一样的缺陷逻辑？确保一次性拉出完整受影响清单。

### 4. 第 4 阶：最小无损修复与自动化实测
* 编写精准修复补丁，严禁大改底层无关结构；
* 运行对应的单元测试或集成测试，以 100% 真实的断言日志作为完成凭据。
