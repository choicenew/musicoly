# Universal Autonomous Engineering & Self-Driven Protocol (通用自主工程与自驱动执行协议)

## 0. 核心定位与原则
本规约是 `developer/skills/` 体系下的核心执行能力规约。
AI 必须具备**极度主动的自驱动（Self-Push）**与**全管线沉思（Full-Pipeline Thinking）**能力。要求 AI **主动推演每一个逻辑细节与上下游管线**，做到“任何一个点都彻底想透之后才开始动手”，彻底摆脱被动响应与让用户一遍遍质问、引导的泥潭。

---

## 第一章：动手前彻底想透“上下游全管线” (Think Through Upstream & Downstream First)

在修改任何代码或提出方案之前，必须独立、透彻地在脑海与代码中完成以下 **6 维管线** 的全盘推演，**任何一个点都必须彻底想明白之后，才允许动手**：

1. **上游入口与用户真实场景 (Upstream Scenario & Input Data)**：
   - 彻底搞清输入源数据的真实形态（带前缀/不带前缀/国际标准/脏字符）；
   - 区分不同交互场景（如自动化前台流转 vs 页面手动测试）。
2. **核心服务与多维参数映射 (Core Service & Multi-Dimension Mapping)**：
   - 深度追踪服务内部数据流动，必要时采用多维度参数透传与联合比对（如原始形态、本地格式、国际格式）；
   - 绝不能拿着单一形态去死磕硬碰。
3. **保护底层核心，绝不侵入基础工具类 (Non-Invasive Core Utilities)**：
   - **铁律**：**严禁随意改动底层核心工具类！**
   - 必须尊重并直接复用已有工具类的封装，**严禁手写抄袭、复制拷贝工具类内部的代码到 UI/Notifier 层！**
   - UI/Notifier 层只能作为使用者，直接调用工具类提供的高级方法，严禁手写零散硬编码前缀判定。
4. **责任边界与隔离 (Clean Architecture & Boundary Isolation)**：
   - 划分清楚“全局通用核心服务”与“特定页面/调试页面”的职责边界；
   - 页面特有的降级补充逻辑只能**收拢在特定页面的 Notifier 入口中**，绝不能滥改底层全局服务，避免波及全局其他正常业务。
5. **下游持久化与存储检索比对 (Downstream Storage & Matching)**：
   - 数据库中存入的标准格式是什么？检索时是否具备归一化标准 + 原始输入保底双重比对？
   - 杜绝因格式微小差异导致明明库里有数据却检索不到。
6. **海量数据与极端边界 (Boundary Cases & Concurrency)**：
   - **海量数据性能**：数据量庞大时，严禁全表载入 Dart 内存筛选，必须走底层物理索引定位；
   - **Isolate 隔离安全**：后台线程执行解析或耗时任务时，绝不能调用 UI 主线程实例（如 `BuildContext`），防止线程崩溃。

## 第二章：真实批评深度反省与纠偏矩阵 (Anti-Pattern Self-Correction)

| 典型反面现象 | 根源分析 | 强制矫正规范 |
| :--- | :--- | :--- |
| **擅自修改底层工具类** | 动不动乱改底层核心工具，甚至在 Notifier 里把工具类的逻辑抄一遍重复实现。 | **严禁动底层核心工具**。先看懂已有实现，100% 直接复用，严禁在 Notifier / UI 层手写抄袭或滥改底层。 |
| **在 Notifier 手写字符串解析判定** | 逻辑散落、没有收拢到位。在 Notifier 里手写 `startsWith` 判定，越界干了工具类该干的事。 | **彻底收拢解析**。删除 Notifier 里所有手写前缀判断，完全由通用工具类自动解析并返回强类型实体。 |
| **管线追踪不全、盲人摸象** | 视野狭窄，只盯单一文件看，没看全核心服务与插件调度的三维参数透传。 | **全管线服务深度串查**。回答与修改前，必须把服务、调度器、过滤器和 DB 仓库链条全部连起来审查。 |
| **空口宣称“完美/成功”** | 修改完代码没有拿出可信的区别对比与自动化测试实测结果。 | **有据可查，必须跑单元测试**。重构后必须运行单元测试，用 100% 全绿的测试日志和清晰的逻辑对比说话。 |
| **模糊场景，扩大改动范围** | 把局部页面的特有调试需求盲目扩大到全局通用服务中。 | **场景隔离 + 降级流水线**。在局部页面实现“优先自动解析 ➔ 失败降级补充”的两级流水线，不污染全局管线。 |
| **依然使用旧式手动 Notifier** | 依然使用旧的手动 `NotifierProvider` 声明。 | **保持现代化 Riverpod 3.0 / 代码生成规范**。统一使用 `@riverpod` 注解。 |

## 第三章：绝对执行与质量铁律 (Absolute Operational Commandments)

1. **绝对用户指令 Supremacy (User Command Supremacy)**：
   - 用户指定的任何参数（组包大小、线程数、模型名称、配置文件名、接口字段、Flutter 环境路径），必须 100% 字对字准确匹配，严禁私自“优化”或篡改。
2. **回答优先准则（先回答，后行动）**：
   - 当用户要求“先回答问题”、“不允许修改任何东西”或提出质问时，**立刻停止一切文件修改和工具调用**，先做彻底、诚实、直接的文本回答。
3. **物理还原指令（真还原）**：
   - 用户指示“还原/reset/restore/撤销”时，必须使用物理还原（如 `git checkout` / `git restore`），严禁用手写重写代替。
4. **编译与测试真实门禁**：
   - 未经过编译校验（`analyze` 报 0 Error）以及真正的自动化单元测试前，严禁口头夸大成果或夸口“100% 修复”。
